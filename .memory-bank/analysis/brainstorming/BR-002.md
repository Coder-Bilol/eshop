# Brainstorming Report - BR-002

## Status
- Date: 2026-08-13
- Facilitator: AI
- Source of product intent: user
- Scope: FT-006 Checkout Delivery Methods
- Recommended next step: /brief

## Problem Space
Authenticated checkout/delivery MVP должен собрать и валидировать checkout snapshot покупателя перед передачей в оплату и созданием заказа. Покупатель выбирает ручной способ доставки, указывает контактные данные и получает понятное восстановление при недоступности выбранного метода.

## Goals
- Поддержать checkout для authenticated buyer.
- Дать стабильный набор способов доставки: `pickup`, `city_courier`, `transport_company`.
- Передать в FT-007 validated checkout snapshot, а в FT-009 выбранный payment ID.
- Оставить FT-006 ответственным за данные и валидацию, не за создание заказа или интеграцию с payment provider.

## Constraints
- Medusa Admin / Shipping Options является источником настроенных тарифов.
- Начальные локальные тарифы: pickup — `0 RUB`, city_courier — `500 RUB`, transport_company — `700 RUB`.
- Поля `name`, `email`, `phone`, `city` обязательны.
- `address` обязателен для `city_courier` и `transport_company`, но не для `pickup`.
- `comment` необязателен.
- Backend выполняет normalization и применяет safe length limits.
- Недоступный способ доставки возвращает HTTP `422` с code `delivery_method_unavailable`; recovery: retry или выбор другого способа.
- Payment IDs: `card`, `sbp`, `sberpay`.
- FT-006 не создает order и не интегрируется с payment provider.

## Techniques Used
- Constraints-first framing.
- MVP slicing по границам FT-006, FT-007 и FT-009.
- Risk-first review для тарифов, валидации и недоступных способов доставки.

## Raw Ideas
- Свести checkout к одному authenticated flow без guest checkout в границах FT-006.
- Хранить выбранный delivery method как стабильный machine-readable ID.
- Рассматривать тариф как runtime-конфигурацию Medusa Admin / Shipping Options, а не как кодовую константу.
- Валидировать условную обязательность адреса на backend.
- Нормализовать входные строки до применения length limits.
- Возвращать структурированную ошибку для unavailable method, чтобы storefront мог повторить запрос или предложить замену.
- Разделить checkout snapshot, order creation и payment-provider integration по feature boundaries.

## Clusters / Themes
- Checkout data: contacts, city, conditional address, optional comment.
- Delivery configuration: three stable options and Admin-managed tariffs.
- Boundary handoff: validated snapshot to FT-007, payment ID to FT-009.
- Failure recovery: `422 delivery_method_unavailable` with retry/select-other paths.
- Scope discipline: no order creation and no external delivery/payment integration in FT-006.

## Selected Directions
- User decision: problem space is authenticated checkout/delivery MVP; target user is authenticated buyer.
- User decision: delivery providers are not integrated externally.
- User decision: tariffs are configured in Medusa Admin / Shipping Options; initial values are `pickup: 0 RUB`, `city_courier: 500 RUB`, `transport_company: 700 RUB`.
- User decision: stable delivery IDs are `pickup`, `city_courier`, and `transport_company`.
- User decision: `name`, `email`, `phone`, and `city` are required; `address` is required only for `city_courier` and `transport_company`; `comment` is optional.
- User decision: backend owns normalization and safe length limits.
- User decision: unavailable delivery method returns `422` with `delivery_method_unavailable`; recovery is retry or select another method.
- User decision: payment IDs are `card`, `sbp`, and `sberpay`.
- User decision: FT-006 passes a validated checkout snapshot to FT-007 and the selected payment ID to FT-009.
- User decision: FT-006 creates no order and does not integrate a payment provider.

## Rejected Directions
- Hardcoded tariffs as the runtime source.
- External carrier integration.
- FT-006 creating a pending order or payment.

## Assumptions
- Medusa Admin / Shipping Options can represent and expose the three selected local delivery options and tariffs.
- The downstream features accept the stated handoff semantics; exact transport schemas remain their responsibility.
- Safe length limits are enforced server-side, but exact numeric limits are not selected here.
- No external research was performed during brainstorming.

## Open Questions

- What precise validated checkout snapshot schema and transport boundary will FT-007 consume?
- What precise payment-ID handoff contract will FT-009 consume?
- Which existing Medusa v2 extension point maps Shipping Options configuration into this checkout flow?
