## 2. Сбой отмены просроченного заказа исключает его из повторной обработки

**Приоритет:** высокий.

В [expire-pending-order.ts](apps/backend/src/workflows/checkout/expire-pending-order.ts) шаг `markExpiryCleanupPendingStep` записывает `checkout_state: "expired"` до вызова `cancelOrderWorkflow`. У шага нет compensation.

Если отмена падает до фиксации native cancellation, заказ остаётся в состоянии native `pending`, logical `expired`, cleanup `pending`. Фильтры в [pending-order.ts](apps/backend/src/checkout/pending-order.ts) больше не выбирают его: `isExpiredPendingOrder` требует `pending_payment`, а `isPendingOrderExpiryCleanupDue` — native `canceled`. Резерв может зависнуть без автоматического восстановления.

**Подтверждение:** offline-вызов helpers для такого состояния вернул `false` для обоих фильтров. Реальный сбой Medusa/PostgreSQL не воспроизводился.

**Минимальное исправление:** сохранять возможность повторной отмены после сбоя; финальное logical состояние `expired` записывать после успешной отмены. Согласовать retry-фильтры с origin и незавершённым cleanup.

**Проверка исправления:** вызвать сбой отмены после записи cleanup metadata; следующий запуск должен повторить отмену и освободить резерв. Повторная успешная обработка должна быть безопасной.

## 4. Единицы фильтра цены не согласованы с отображением

**Приоритет:** средний.

Поля `price_min` / `price_max` в [page.tsx](apps/storefront/app/page.tsx) отправляют ввод без преобразования. [catalog.ts](apps/storefront/lib/catalog.ts) передаёт параметры неизменными, но `formatCatalogMoney` отображает `amount / 100`. Backend в [query.ts](apps/backend/src/catalog/query.ts) сравнивает пределы с исходным `variant.price.amount`.

Например, raw amount `250000` отображается как `2500 ₽`, но при максимальной цене `3000` товар исключается из выдачи: сравнение выполняется как `250000 <= 3000`.

**Подтверждение:** статический разбор цепочки ввода, запроса, сравнения и отображения. Browser reproduction не запускался.

**Минимальное исправление:** сначала уточнить денежные единицы действующего backend-контракта, затем согласовать с ними форматирование, ввод, выбранные значения и placeholders. Не вводить умножение на 100 без проверки контракта Medusa.

**Проверка исправления:** товар с отображаемой ценой 2500 ₽ попадает в диапазон 2000–3000 ₽ и исключается при максимуме 2000 ₽; выбранные значения сохраняют единицы после отправки формы.

## 5. Checkout загружает всю историю заказов для проверки idempotency

**Приоритет:** средний; технический долг производительности.

В [create-pending-order.ts](apps/backend/src/workflows/checkout/create-pending-order.ts) шаг `loadPendingOrderPreparationStep` вызывает `listOrders({}, { relations: ["items"], take: null })`, затем ищет заказ по idempotency key или корзине в памяти.

Это выполняется при первом оформлении и retry. Объём чтения, потребление памяти и стоимость каждого checkout растут вместе со всей историей магазина, включая строки заказов.

**Подтверждение:** прямое чтение реализации. Нагрузочные измерения не проводились.

**Минимальное исправление:** фильтровать кандидатов на уровне БД, сохраняя существующую семантику поиска по idempotency key и корзине; строки подгружать только для найденного заказа. Проверить поддержку фильтрации по metadata текущим Medusa API. Новый сервис или отдельный ledger не требуется; необходимость индекса оценить по полученному запросу.

**Проверка исправления:** retry возвращает прежний заказ; конфликт ключа с другим содержимым отклоняется; повторное оформление корзины не создаёт дубликат; проверки владельца и резервов сохраняются. Убедиться, что запрос больше не читает все заказы и их строки.
